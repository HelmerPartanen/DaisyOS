# DaisyOS Rust + Slint migration ledger

This is an implementation in progress, not a declaration that the desktop has
been migrated. Existing Avalonia entry points remain the shipping default until
visual and functional parity gates pass. No Continuity input/capture service,
KWin plugin, production daemon, or user configuration is replaced by this work.

## Source audit

The deterministic [inventory](avalonia-inventory.json), generated by
`scripts/audit-avalonia-ui.py`, records **631 first-party C#/XAML/project files,
94 XAML files, 526 C# files, and 112,539 lines** in `src/` (excluding generated
build directories). It includes paths, hashes, classes, XAML resources/resource
consumers, named event handlers, NuGet dependencies and project references.
This is a lexical inventory; the architectural conclusions below come from
reading the implementations. Assets and the pinned Avalonia fork are not
counted as first-party C# files.

| Area | Source of truth | Migration decision |

| Composition/lifetime | `src/DaisyOS.Shell/App.axaml.cs`, `Program.cs`, `Services/StandaloneApplication.cs` | Most app executables reference the entire shell. Move state/logic into Rust crates before replacing entry points. Preserve activation and window identity. |

| Runtime appearance | `Services/Appearance/*`, `Services/Theming/*`, `App.axaml.cs` | Existing camelCase JSON, numeric theme/accent enums, font/scale, high contrast, reduced motion, and timezone-based automatic theme. Keep user data and unknown fields. |

| Files/picker | `Apps/Files/*` plus services | Preserve async enumeration, mutation coordination, sorting/selection, symlinks, metadata, DnD/clipboard, thumbnails and portal semantics. Keep functioning implementation until all consumers migrate. |

### Dependency and reuse boundaries

`DaisyOS.{Files,Mail,Notes,Settings,DiskManager,AppInstaller}` currently depend on
`DaisyOS.Shell`, which supplies shared UI, styles, localization and lifetimes.
The shell depends on Core/System, the pinned Avalonia.Wayland implementation,
Skia/HarfBuzz, DBus, and application-specific libraries (including MailKit,
AvaloniaEdit/TextMate, ONNX and SVG). Merely changing each small `Program.cs`
would retain or lose that whole dependency graph.

Reusable directly: original SVG/PNG/TTF assets and licenses; external D-Bus and
native helper protocols; user JSON/files and low-level daemon processes.
Translate: view models/state machines, XAML templates/resources, interaction
states and application event handling. Replace with Slint facilities: bindings,
layout, focus/input dispatch, declarative animation and ordinary window rendering.
Do not port Avalonia's control/layout engine into Rust.

Notable consolidation candidates: duplicated caption controls, application
styles inheriting the same button semantics, repeated settings rows, selection
indicators, input styles and scrollbar templates. Calculator's standard and
scientific modes share the same arithmetic keypad; the Slint port uses one model.

### Risks found before switching any routes

- The dock, shell overlays and lock surfaces require special roles. winit's
  ordinary window cannot be assigned layer-shell after Slint has mapped it.
- Slint's pinned winit 0.30 backend supports KDE **whole-surface** blur, but its
  public `set_blur` API does not expose DaisyOS's regional scanline masks. A
  normal calculator window does not establish shell-region parity.
- Source documentation is partly stale: actual blue/accent values, input sizes
  and default font differ from older prose. Generation reads XAML and current
  runtime accent/contrast behavior instead of inventing a new palette.
- Font shaping, focus traversal, IME/preedit, fractional scales, scroll momentum,
  accessibility and spring transitions need explicit visual/input acceptance.
- The active depth presenter is custom media/ONNX rendering, not a generic
  rectangle. It stays in Avalonia until a feature-complete equivalent exists.
- Shipping a partial Notes/Files/Settings replacement would discard features.
  Keep their working implementations and do not silently route users to a demo.

## Architecture and current slice

The root Cargo workspace separates `daisy-core` (framework-independent logic),
`daisy-ui` (DaisyUI Slint components/tokens and runtime theme mapping), and
`daisy-platform` (normal Wayland/KWin integration and diagnostic capture).
Apps are under `apps/`. Existing native Rust services are excluded from this
workspace so their locked dependencies and special release/no_std profiles stay
unchanged. The UI pins Slint 1.18.1 and uses winit/Wayland with Slint's software
renderer and accessibility support. It does not introduce a second UI framework
or software background blur. Renderer selection is a measured migration choice,
not a claim of optimal animation performance for every future shell surface.

On the actual target KWin, only the newer `ext_background_effect_manager_v1`
was advertised; the pinned winit backend only implemented legacy KDE blur.
The adapter therefore borrows the existing winit display/surface with two
localized, documented unsafe conversions. A guest wayland-backend connection
owns only its additional protocol objects and a private event queue; it never
opens another socket, adopts/destroys the window, reads the shared display, or
replaces winit's event loop. Startup polls dispatch only that queue and stop
once negotiated; resize/redraw events keep surface-local regions up to date.
RAII teardown releases the effect/manager before the app backend is dropped.
The protocol permits the effect to become inert when the surface disappears.
The application renders translucent material; KWin supplies background blur.
The older KDE protocol remains a fallback through winit. Rounded-mask geometry
is ported/tested, but overlay-region lifecycle and visual fidelity remain gates.

Generated resources are checked against `DaisyTheme.axaml`. Runtime theme code
reads existing `appearance.json`, handles case-insensitive property names and
numeric enums, derives accent hover/press/contrast with the source algorithm,
and observes appearance changes off the UI thread. It does not write user data.

## Ordered remaining work and cutover gates

1. Finish foundation verification: clean build, real Wayland display, embedded
   fonts/icons, config compatibility, normal-window blur protocol and snapshots.
2. Calculator: differential state-machine parity; keyboard/mouse/focus behavior;
   equivalent original/Slint screenshots for standard/scientific, light/dark,
   accent/high contrast, fonts and 100/150/200% scale. Confirm KWin decoration
   identity, fullscreen and activation/single-instance semantics. Only then route
   the shell's calculator action to the native executable and retire old UI.
3. DaisyUI: current slice provides buttons/icon buttons, text, cards/glass,
   separators, text inputs and switches. Complete selection controls, sliders,
   scrollbars, dropdowns, tabs/navigation, menus, dialogs and tooltips from
   their actual templates and consumers. Test focus, accessibility and IME.
4. Complete platform adapter for pre-map layer-shell roles, output affinity,
   exclusive zones, visibility/input policy, rounded/multiple blur masks and
   scale/resize transactions. Validate against existing multi-monitor tests.
5. Migrate app flows in dependency order: Settings categories and shared dialogs,
   Calendar, Notes editors/storage/handoff, Files/picker/preview, diagnostics,
   Mail and installer/package flows. Keep real service APIs and error paths.
6. Migrate desktop, dock, top bar, launcher, notifications, lockscreen and widget
   surfaces only after the platform and component gates pass. Preserve the
   Continuity session authority and existing capture/input integrations.
7. Switch publishing/session/desktop entry routes per validated app; remove C#
   types/resources only after checking actual consumers and passing regression
   tests. Remove Avalonia dependencies after the final shell surface is replaced.

Verification results and exact limitations are appended as implementation tests
are completed. No phase is complete solely because its code compiles.

## Implemented/verified in this execution

The workspace, generated tokens/selected RESX messages, seven shared primitives,
Calculator's complete state machine and standard/scientific Slint views,
interactive gallery, appearance observer and ext-background-effect adapter are
implemented. Exact logic comparison, Slint input tests, native scale/theme
captures and protocol evidence passed. See [verification](VERIFICATION.md) for
commands, artifacts and material limits. Calculator's shared arithmetic grid,
header alignment, circular backspace affordance, original icon assets and
resolved template text weight were compared with the Avalonia review captures.
The original history glyph has no handler; it remains decorative instead of
introducing a fake working history feature.

This is not a production cutover. The remaining work above is intentional,
concrete and still required. The existing desktop, app routes, and Continuity
input behavior remain the functioning implementation during the migration.
