# Continuity v1 protocol

Implementation: `src/DaisyOS.Continuity`. Contract:
`protocol/continuity/v1/continuity.proto`. Checked-in C# bindings are generated by
protoc 36.1; reproduce with `scripts/generate-continuity-protocol.sh`. The runtime
is Google.Protobuf 3.36.2 with a NuGet lockfile; no Rust process or runtime bindings
are required by this implementation. The stable version was verified against the
[package publisher](https://www.nuget.org/packages/Google.Protobuf/3.36.2).

## Transport choice

The repository's existing runtime is C#/.NET 10. This implementation reuses it
with TLS 1.3 over **TCP 47621**, and DNS-SD **`_daisycont._tcp.local.`**. This adapts
the proposed Rust/Quinn/UDP architecture: the host lacks libmsquic, there is no
existing Rust service workspace, and the platform TLS engine provides certificate
validation without a custom accept-all verifier. One operation owns one bounded
TLS connection; file and clipboard concurrency are budgeted separately. There is
no HTTP API, cloud rendezvous, WAN fallback, plaintext feature traffic, or assumption
that the earlier mock peer controller implements authentication.

The TCP adaptation does not implement multiplexed QUIC streams, input latency
priorities or persistent idle peer sessions. Those remain architecture work before
release-two input/media support. No wire compatibility with the proposed UDP
prototype is claimed. See OPERATIONS.md for firewall/setup changes.

## Bootstrap and mutual TLS

Each side first sends a length-framed **public Bootstrap**: major version, DER
certificate, cosmetic name, operation pairing flag, listening port. Limit 8192
bytes total / 4096 certificate bytes / 256 name characters. No secrets or feature
data appear in bootstrap. Name, address, port and discovery ID are untrusted hints.

The certificate is loaded as an explicit custom trust anchor in .NET's X509 chain
policy. SslStream performs normal TLS 1.3 signature/expiry/EKU/chain validation and
client-side DNS-name validation (`daisycont.local` SAN). Both sides present a client/
server certificate and then require the actual TLS peer certificate to exactly
match its public bootstrap. There are no certificate-verification callbacks.
For existing peers, bootstrap's SHA-256 identity must already be remembered and
must match the expected outbound identity. Merely supplying a self-signed root
never grants trust or feature permissions.

For unknown candidates only pairing is admitted, while an active user session
has explicitly enabled visibility. Each local UI shows both **full SHA-256
certificate fingerprints**. The human must compare both directions against the
other physical device and approve locally on both. Only then are certificate pin
and default-off capabilities stored. This is full public-key fingerprint
verification, not a six-digit PIN, PAKE implementation, truncated transcript hash
or invented SAS. TLS proves possession of the fingerprinted private keys. A local
prompt is bound to this live TLS operation and expires after two minutes; a trust
epoch and cancellation prevent an earlier approval reviving a revoked peer.

This pairing implementation has not received an independent protocol/security
review. Do not claim audited pairing or completed release acceptance. See SECURITY.md.

## Authenticated envelopes

After TLS, both sides exchange Hello (major=1, minor=0, certificate identity,
32-byte fresh nonce, supported clipboard/files capabilities). Identity must match
TLS; a Hello/discovery claim cannot establish authority. Every subsequent envelope
has a 16-byte request ID. Unknown fields may be skipped, but absent/unknown message
kind, wrong major, malformed IDs and inappropriate operations are rejected.

Framing: unsigned four-byte big-endian length followed by precisely that many
Protobuf bytes. Reject zero or lengths above 1,052,672 before allocation. The public
bootstrap has a lower cap. EOF mid-header/body is an error; an invalid/partially
written connection is closed. Authentication/bootstrap have ten-second deadlines;
operation reads, pairing decisions and transfer inactivity have finite deadlines.
The daemon bounds incoming connections and outgoing feature work rather than
spawning a task for every unbounded request.

Pairing connections process only consent. Trusted feature connections process one
Ping/Pong, clipboard flow or file flow. Receiver checks current active-session,
pause/enabled state, live trust and explicit per-peer permission; socket connection
and negotiated capability alone authorize nothing. Lock, pause, owner loss,
disconnect and revoke invalidate operation lifetimes and source ownership.

## Clipboard

Offer includes random update ID, authenticated origin ID, one canonical
`text/plain;charset=utf-8` MIME, bounded size and SHA-256. Receiver requests only
that format, then validates matching ID/length/digest and strict UTF-8. Maximum text
is 1 MiB. A bounded expiring origin/update cache rejects duplicates. A bounded five-minute injected-content digest cache suppresses delayed rebroadcast.
It can also suppress a genuine re-copy of a recently received value; an origin-aware
native adapter is still required for complete clipboard semantics. No PRIMARY
or clipboard history synchronization occurs. Unsupported Wayland data-control is
reported unavailable. Clipboard payloads are not persisted/logged. Owned byte
buffers are cleared after use; managed serialization and external clipboard sources
cannot promise erasure of every copy from process memory.

## Files

Offer is one basename, 16-byte transfer ID, length (maximum 100 GiB) and SHA-256.
Receiver decides consent and destination; no peer-supplied destination path exists.
Chunk offsets must exactly equal the receiver position, chunks are 1–65536 bytes,
and no chunk may pass declared length. Completion requires exact length and hash.

Private resume records bind peer identity, basename, length, digest, the current permission-grant identity and 24-hour
specific-manifest consent. Resume offset is the actual partial-file size, never a
network path. Unknown schemas, unsafe paths, concurrent duplicate manifests and
oversized records fail closed. Corrupt data is discarded. Explicit cancellation/
permission/session failures invalidate approval; transport interruptions may resume.
Completion receipts recover lost acknowledgements without publishing duplicate files.
Revoking/re-pairing or disabling a permission invalidates earlier grant-bound consent.
After sender restart, reselect the unchanged file to recover. There is no outgoing
crash-restart queue or folder-tree protocol yet.

The completed file is streamed to a private temporary file on the Downloads
filesystem, flushed, and renamed without overwriting an existing entry. Final
publication rechecks current policy under the same service lock as revoke/pause.
Only then is verified FileComplete acknowledged and an actionable notification sent.

## Local IPC and persistence

Session D-Bus: name/interface `org.daisyos.Continuity1`, object
`/org/daisyos/Continuity1`, method `Execute(s)->s`. JSON command/status structures
are generated for C# serialization in DaisyOS.Core. This is **local IPC**, separate
from the network Protobuf contract. UID is checked using the bus daemon. Session
authorization additionally requires the live unique owner of
`org.daisyos.ContinuitySession1` plus the correct active/unlocked logind user session.

State schema version 1 contains opt-in preferences and certificate-bound trust
records with default-off clipboard/files grants. Identity.pfx is separate. Unknown
versions fail startup rather than dropping grants or accepting defaults. A per-state
lock prevents two daemons sharing one identity. Identity cloning/reset requires
explicit operational handling, not automatic trust migration.

The earlier Core peer-session/mock interfaces remain isolated reusable prototypes;
no raw C# runtime object is transmitted over the network by this daemon.

## Media/handoff extension (minor revision 1)

Hello now advertises `INPUT`, `HANDOFF`, `SCREEN`, and `AUDIO`. New initiators
require the corresponding peer capability before requesting a feature. Separate
TLS connections carry `LiveStart` (session ID/kind/control), `LiveDecision` and
strictly sequenced `LivePacket` messages. Audio uses exactly 3840 bytes per packet
(48 kHz stereo s16le, 20 ms); reverse empty packets provide liveness. Screen
packets hold at most 512 KiB and validate JPEG SOF dimensions to 1280 × 720 before
decoding; empty packets keep static screens alive. Reverse packets contain at
most 128 bytes of validated numeric input, with empty liveness packets. Input
uses evdev codes, normalized selected-monitor coordinates and bounded queues.
`ActivityOffer` carries an allowlisted app/kind/schema/title/text snapshot and
`ActivityResult` returns the target's decision. No network fields select an
executable, command, destination path, GStreamer pipeline or PulseAudio module.
See [MEDIA_AND_HANDOFF.md](MEDIA_AND_HANDOFF.md) for permissions and lifecycle.

## Screen-edge input links

The separate `EDGE_INPUT` capability advertises live kind `input`. It uses an
InputCapture/libei receiver on the source and a RemoteDesktop/libei sender on
the destination, without a video stream. LivePacket payloads are bounded to
128 bytes and strictly sequenced in both directions; empty packets are liveness
messages. Numeric input kinds 1–4 retain their evdev/relative-motion meaning.
Kind 6 carries an entry side (0 left, 1 right, 2 top, 3 bottom) and a normalized
entry fraction. Kind 7 releases emulation and carries the proportional return
fraction. The source releases its compositor capture at that position. Native
helpers release emulation/capture on EOF, portal revocation or process loss.
Receive liveness deadlines are four seconds; active grants are not persisted or
automatically restored across disconnects. Explicitly revoked receiving grants
are distinguished from never-requested capabilities by a private blocked mask.

Idle audio outputs may send empty forward packets to preserve liveness before
a player starts; data packets remain exactly 3840 bytes of the fixed PCM format.
Audio and handoff grants approved locally can be remembered for the paired
identity, while screen/input sessions still require the system portal consent.
